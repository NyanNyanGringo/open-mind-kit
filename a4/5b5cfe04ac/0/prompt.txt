```text
# ПРИНЦИПЫ КАЧЕСТВА


> Ниже — необсуждаемые принципы. Любая фича, интеграция и изменения схемы данных должны им соответствовать.

## Security / Privacy

Мы проектируем систему так, чтобы утечка данных была максимально маловероятна и максимально мало вредила: собираем и храним минимум, даём пользователю контроль, а доступ к данным ограничиваем “по необходимости”. Любая автоматизация (интеграции, AI, импорт) — только по явному согласию, с прозрачным описанием, что и куда уходит. Секьюрность и приватность — это свойства архитектуры, а не “фича на потом”.

## Performance

Система должна оставаться быстрой при “бесконечной” истории операций и росте активных пользователей: мы проектируем чтение/фильтрацию/агрегации как основные пути, закладываем бюджеты запросов и избегаем N+1 и тяжёлых сканов. Производительность — это также предсказуемость (p95/p99) и деградация без падений. Любая новая сущность или экран обязаны иметь понятный план индексации и пагинации.

## Scalability
Рост пользователей и данных не должен требовать переписывания системы. Мы проектируем горизонтальное масштабирование там, где это разумно, и отделяем вычисления от хранения. Архитектурные решения оцениваются с точки зрения роста на порядок, а не на проценты.

## Backward Compatibility
Любые изменения API, схемы или поведения должны учитывать существующих клиентов и данные. Депрекация — управляемый процесс с явными сроками и коммуникацией. Ломающие изменения допустимы только при наличии стратегии миграции.

## Explicitness
Поведение системы должно быть очевидным и предсказуемым. Неявные сайд-эффекты, «магические» автозаполнения и скрытые фоновые изменения состояния недопустимы без прозрачного описания. Лучше явная конфигурация, чем неочевидная автоматика.

## UX Consistency
Пользовательский опыт должен быть логичным и единообразным: одинаковые действия ведут к одинаковым результатам во всех частях системы. Ошибки формулируются понятно и помогают исправить проблему. Мы минимизируем когнитивную нагрузку и не заставляем пользователя догадываться о правилах.

## Testability
Любая бизнес-логика должна быть проверяема автоматически. Мы проектируем систему так, чтобы ключевые сценарии можно было покрыть тестами без сложной инфраструктурной магии. Интеграционные и нагрузочные тесты обязательны для критических путей.

## Не дублируй код
- Код не дублируется и не повторяется. Если модуль общий или универсальный, он должен находиться внутри utilities.
- Всегда проверяй код на дубликаты, если уверенность в том, что нет дублей < чем 0.1

## Пиши простой и понятный код
- Используйте синтаксис и логику, которые легко поймёт junior-разработчик. Код должен быть очевидным при первом чтении и не требовать дополнительных пояснений.
```

## Quick Guidelines

- Focus on **WHAT** users need and **WHY**.
- Avoid HOW to implement (no tech stack, APIs, code structure).
- Written for business stakeholders, not developers.
- DO NOT create any checklists that are embedded in the spec. That will be a separate command.

### Section Requirements

- **Mandatory sections**: Must be completed for every feature
- **Optional sections**: Include only when relevant to the feature
- When a section doesn't apply, remove it entirely (don't leave as "N/A")

### For AI Generation

When creating this spec from a user prompt:

1. **Make informed guesses**: Use context, industry standards, and common patterns to fill gaps
2. **Document assumptions**: Record reasonable defaults in the Assumptions section
3. **Limit clarifications**: Maximum 3 [NEEDS CLARIFICATION] markers - use only for critical decisions that:
   - Significantly impact feature scope or user experience
   - Have multiple reasonable interpretations with different implications
   - Lack any reasonable default
4. **Prioritize clarifications**: scope > security/privacy > user experience > technical details
5. **Think like a tester**: Every vague requirement should fail the "testable and unambiguous" checklist item
6. **Common areas needing clarification** (only if no reasonable default exists):
   - Feature scope and boundaries (include/exclude specific use cases)
   - User types and permissions (if multiple conflicting interpretations possible)
   - Security/compliance requirements (when legally/financially significant)

**Examples of reasonable defaults** (don't ask about these):

- Data retention: Industry-standard practices for the domain
- Performance targets: Standard web/mobile app expectations unless specified
- Error handling: User-friendly messages with appropriate fallbacks
- Authentication method: Standard session-based or OAuth2 for web apps
- Integration patterns: RESTful APIs unless specified otherwise

### Success Criteria Guidelines

Success criteria must be:

1. **Measurable**: Include specific metrics (time, percentage, count, rate)
2. **Technology-agnostic**: No mention of frameworks, languages, databases, or tools
3. **User-focused**: Describe outcomes from user/business perspective, not system internals
4. **Verifiable**: Can be tested/validated without knowing implementation details

**Good examples**:

- "Users can complete checkout in under 3 minutes"
- "System supports 10,000 concurrent users"
- "95% of searches return results in under 1 second"
- "Task completion rate improves by 40%"

**Bad examples** (implementation-focused):

- "API response time is under 200ms" (too technical, use "Users see results instantly")
- "Database can handle 1000 TPS" (implementation detail, use user-facing metric)
- "React components render efficiently" (framework-specific)
- "Redis cache hit rate above 80%" (technology-specific)

## Decision 3: Database — SQLite with WAL mode

**Decision: SQLite with WAL mode enabled**

**Rationale:**

- Zero-server: runs as a library inside the FastAPI process, no additional container needed
- WAL (Write-Ahead Logging) mode resolves the classic SQLite concurrency concern. With WAL, multiple concurrent readers never block each other or the writer. The Stack Overflow and Reddit community consensus (2025) confirms: `PRAGMA journal_mode=WAL` is the correct production setting for SQLite with async Python
- SQLite is 35% faster than the filesystem for small BLOBs (per official SQLite benchmark), and 20% more storage-efficient — important for thumbnail/preview caching
- `aiosqlite` (v0.22.1) provides fully async-compatible SQLite access, and `SQLModel` (combining SQLAlchemy + Pydantic) gives a clean ORM layer
- Entire database is a single file: trivially portable, backupable with `cp`, inspectable with any SQLite browser
- For large files (PDFs, audio, video), store on local filesystem + store metadata (path, size, checksum, processing status) in SQLite — this is the recommended pattern for blobs over ~50KB (per SQLite documentation)
- Alembic 1.18.4 handles schema migrations cleanly on top of SQLModel/SQLAlchemy

**Configuration:**

## Decision 4: Task Queue — ARQ + Redis

**Decision: ARQ with Redis**

**Rationale:**

FastAPI `BackgroundTasks` is explicitly ruled out by FastAPI's own documentation: "If you need to perform heavy background computation, you might benefit from using other bigger tools like Celery." Critically, `BackgroundTasks` runs in the web server process, has no status tracking, loses tasks on server restart, and cannot be queried. For a file processing pipeline where users need to see "Processing... 60% complete" or "Failed: corrupted PDF", this is a non-starter.

Celery is the industry workhorse but brings significant complexity: it is not async-native (requires gevent/eventlet workarounds or the new `celery[gevent]` mode), has a large dependency footprint, and the community in 2025 consistently describes it as "clunky for async" and "overkill" for single-process local deployments.

ARQ (Async Redis Queue) is the right fit because:
- Async-native: every task function is a regular `async def`, integrates with FastAPI's async code naturally
- Requires only Redis (one extra Docker Compose service, lightweight)
- Job status tracking built in via Redis hashes: you can query `job.status` and `job.result` at any time
- Supports retries, timeouts, scheduled jobs, and job deferral out of the box
- Substantially lighter than Celery; the codebase is small and auditable
- Community consensus in 2025 (r/Python, multiple benchmarks): ARQ is the recommended choice for asyncio-native Python services
- SAQ (Simple Async Queue) is also a valid alternative with lower latency (<5ms vs ARQ's ~500ms polling default), but ARQ has a larger community and more production references for FastAPI

The architecture: FastAPI enqueues a job, returns a `job_id` immediately. The ARQ worker (same Docker service or a separate one) processes it. The frontend polls `GET /jobs/{job_id}/status` or uses Server-Sent Events for real-time updates. Redis stores the job state.

**Key versions:**
```
arq==0.26.x   # check PyPI; actively maintained
redis==5.x    # redis-py client
```

Docker Compose addition:
```yaml

  image: redis:7-alpine
  volumes:
    - redis_data:/data
```

**Alternative without Redis:** If you want zero external broker, a SQLite-backed queue using `persist-queue` or a custom table with `SELECT ... FOR UPDATE SKIP LOCKED` (SQLite WAL) is viable for a single-worker local app. This eliminates the Redis container at the cost of polling-based job discovery and higher implementation complexity. ARQ + Redis is still recommended for the better DX and status tracking.

**Decision: Local filesystem for file bodies, SQLite for metadata**

**Rationale:**

Storing large files (PDFs, audio, video) as BLOBs in SQLite is not appropriate. The SQLite documentation itself recommends keeping BLOBs in the database only for items under ~50KB. The correct pattern (per all major sources, including Medium, SQLite docs, and DBA Stack Exchange):
- **File bodies** go to the local filesystem in a structured directory under a Docker volume (e.g., `/data/uploads/{year}/{month}/{file_id}/original.pdf`)
- **Metadata** (original filename, MIME type, file path, size, checksum, upload timestamp, processing status, extracted text, AI output) stored in SQLite

This gives you:
- Full streaming support for large files (FastAPI's `FileResponse` and `StreamingResponse`)
- Efficient random-access reads (audio seeked by timestamp, video range requests)
- SQLite for all query/filter/search operations on metadata and processing results
- Small blobs like thumbnails or image previews (<50KB) CAN be stored in SQLite and will actually be faster than filesystem access by 35%
- Simple backup: `tar` the `/data` volume + copy the `.db` file

**Docker volume structure:**

```
  uploads/          # original files, organized by ID
  processed/        # extracted text, transcripts, thumbnails
```

# Spaced Repetition Algorithm Research: Structured Summary for Study-Kit MVP

## 1. SM-2 Algorithm (SuperMemo 2)

### How It Works

SM-2 is a deterministic scheduling algorithm developed in 1987. It operates on a simple mathematical rule: after each review, compute a new interval based on how well the user recalled the item, then schedule the next review at `today + interval` days.

**Quality Rating Scale (0-5):**

| Grade | Meaning |
|-------|---------|
| 5 | Perfect response, no hesitation |
| 4 | Correct after slight hesitation |
| 3 | Correct despite serious difficulty |
| 2 | Incorrect but correct answer seemed easy |
| 1 | Incorrect, correct answer recalled afterward |
| 0 | Complete blackout |

**Algorithm Steps:**

```
# Step 1: Update Easiness Factor
EF' = EF + (0.1 - (5 - Q) * (0.08 + (5 - Q) * 0.02))
EF' = max(EF', 1.3)   # floor at 1.3

# Step 2: Compute new interval
if Q < 3:             # incorrect
    repetitions = 0
    interval = 1
elif repetitions == 0:
    interval = 1
elif repetitions == 1:
    interval = 6
else:
    interval = ceil(interval * EF')

# Step 3: Increment repetitions on success
if Q >= 3:
    repetitions += 1

# Step 4: Schedule next review
next_due = today + interval (days)
```

**Fields Required Per Card (SM-2):**

| Field | Type | Default | Range | Purpose |
|-------|------|---------|-------|---------|
| `repetitions` | integer | 0 | 0..∞ | Consecutive correct streak |
| `ease_factor` | float | 2.5 | 1.3..2.5 | Difficulty multiplier |
| `interval` | integer (days) | 0 | 1..∞ | Days until next review |
| `due_date` | date | now | - | When this card is next due |

Plus review history (separate table):

| Field | Type | Purpose |
|-------|------|---------|
| `reviewed_at` | timestamp | When the review happened |
| `quality` | integer (0-5) | User's self-rating |

**SM-2 Limitations:**
- Fails to adapt to individual memory patterns; uses fixed mathematical rules
- A single incorrect answer resets the card to day 1 regardless of prior mastery (no "ease hell" protection)
- Does not model actual probability of recall
- Handles delayed reviews poorly (if you review 10 days late, the algorithm does not know)

## 2. FSRS (Free Spaced Repetition Scheduler)

### How It Works

FSRS is a modern ML-derived algorithm based on the **DSR model** (Difficulty, Stability, Retrievability — a "Three-Component Model of Memory"). It was validated against millions of Anki reviews and is now the default algorithm in Anki 23.10+.

**Core Memory Model:**

- **Stability (S):** Real number in [0, ∞], measured in days. Represents how long it takes for retrievability to decay from 1.0 to 0.9. Higher S = longer retention.
- **Difficulty (D):** Real number in [1, 10]. Captures inherent item complexity. Persists and is updated on each review.
- **Retrievability (R):** Probability of recall RIGHT NOW. Computed dynamically, never stored.

**Retrievability Formula (FSRS v5):**

```
R(t, S) = (1 + (19/81) * (t / S)) ^ (-0.5)
```

where `t` is days since last review and `S` is current stability. This is a power-law forgetting curve (not exponential).

**Scheduling Formula:**

Given a target retention rate `r_d` (typically 0.90):

```
next_interval = (S / (19/81)) * (r_d ^ (1 / -0.5) - 1)
             = (S / (19/81)) * (r_d ^ (-2) - 1)
```

**Stability Update (on correct recall):**

```
S' = S * α(D, S, R, grade)
```

Where α is a complex function of 19 learned weight parameters (W array) trained from aggregate review data. Default parameters are provided and work well without per-user training.

**Stability Update (on failure):**

```
S' = min(S_failure_formula(D, S, R), S)
```

Critically, failure does NOT reset to day 1. The card is re-scheduled conservatively based on its prior stability.

**Fields Required Per Card (FSRS):**

| Field | Type | Default | Range | Purpose |
|-------|------|---------|-------|---------|
| `stability` | float | — | [0, ∞) | Days for R to drop from 100% to 90% |
| `difficulty` | float | — | [1, 10] | Item inherent difficulty |
| `due_date` | date | now | — | Next scheduled review date |
| `last_review_date` | date | null | — | Used to compute elapsed `t` for R |
| `state` | enum | `new` | new/learning/review/relearning | Card lifecycle state |
| `step` | integer | 0 | 0..N | Position in learning/relearning steps |

Plus review history (separate table):

| Field | Type | Purpose |
|-------|------|---------|
| `reviewed_at` | timestamp | When the review happened |
| `rating` | integer (1-4) | Again/Hard/Good/Easy |
| `stability_before` | float | For audit/debugging |
| `difficulty_before` | float | For audit/debugging |

Note: FSRS uses a 1-4 rating scale (Again=1, Hard=2, Good=3, Easy=4), not 0-5.

## 3. Simple Interval-Based vs. ML-Based: What Is Appropriate for MVP?

| Criterion | Simple Interval (custom) | SM-2 | FSRS |
|-----------|--------------------------|------|------|
| Implementation complexity | Very low | Low | Medium |
| Scheduling accuracy | Poor | Moderate | High |
| Handles irregular reviews | No | No | Yes |
| Handles failure gracefully | No (reset) | No (reset) | Yes (partial decay) |
| Open-source implementations | Many | Many | Many (TypeScript, Python, Go, Rust) |
| Mastery score available | Crude | Approximate | Native (R = probability) |
| Requires training data | No | No | No (defaults provided) |
| User-visible "why" | Easy | Easy | Opaque (ML weights) |

**Verdict for MVP:** SM-2 is the pragmatic choice for a first version. FSRS is architecturally superior but adds complexity. However, if you are building a greenfield app in 2025, **FSRS is worth using from the start** because:
1. Pre-trained default parameters (W array with 21 values) are published and work without any training data
2. Open-source reference implementations exist in TypeScript/Python that can be dropped in
3. The data model is barely more complex than SM-2 (add `stability` + `difficulty` fields; remove `ease_factor` + `repetitions`)
4. Retrievability gives you a natural, mathematically meaningful mastery score (0.0–1.0) for free

The "ML" complexity in FSRS is pre-computed; you just use the published default weight array. You are not building or training a model.

## 6. Mastery Score / Knowledge Rating Formula (0-100%)

### Primary Score: Retrievability (FSRS native)

```
R(t, S) = (1 + (19/81) * (t / S)) ^ (-0.5)

mastery_score = R * 100   -- expressed as 0–100%
```

Where:
- `t` = `now() - last_review_date` in fractional days
- `S` = `stability` from the knowledge_items row
- For `state = 'new'` (never reviewed): `mastery_score = 0`
- For `state = 'learning'` (in initial learning steps): `mastery_score = 10 * (step / total_steps)`

This score naturally decays between sessions (as memory fades) and jumps after each successful review. It is a real-time probability, making it the most honest possible "do you know this?" metric.

### Weak Area Identification

An item is a "weak area" when any of:

```
-- Retrievability below threshold (likely to forget)
R < 0.70

-- High difficulty (hard to learn)
difficulty > 7.0

-- High lapse rate (repeated failures after maturity)
lapse_count > 2 AND total_reviews > 5

-- Overdue and not reviewed
due_date < CURRENT_DATE - INTERVAL '3 days'
```

For topic-level weak areas, aggregate per `topic_id`:

```sql
SELECT
    topic_id,
    AVG(mastery_score)          AS avg_mastery,
    COUNT(*) FILTER (WHERE mastery_score < 70) AS weak_item_count,
    COUNT(*)                    AS total_items
FROM knowledge_items_with_scores  -- view computing R dynamically
WHERE user_id = $1
GROUP BY topic_id
ORDER BY avg_mastery ASC;
```

### Session Scheduling Query (What to Show Next)

```sql
-- Items due now (core spaced repetition queue)
SELECT * FROM knowledge_items
WHERE user_id = $1
  AND due_date <= CURRENT_DATE
ORDER BY
  CASE state
    WHEN 'learning'    THEN 0   -- highest priority: active learning
    WHEN 'relearning'  THEN 1   -- second: items just failed
    WHEN 'review'      THEN 2   -- third: mature cards due

```

### Dashboard Progress Metrics

```sql
-- Per-user summary
SELECT
    COUNT(*)                                           AS total_items,
    COUNT(*) FILTER (WHERE state = 'new')              AS not_started,
    COUNT(*) FILTER (WHERE state IN ('learning','relearning')) AS in_progress,
    COUNT(*) FILTER (WHERE state = 'review')           AS mature,

    -- Average mastery: use stored retrievability approximation
    -- (recomputed at query time for accuracy)
    ROUND(AVG(
        CASE
          WHEN stability IS NULL THEN 0
          ELSE POWER(1 + (19.0/81) * (EXTRACT(EPOCH FROM (now() - last_review_date)) / 86400) / stability, -0.5) * 100
        END
    ), 1)                                              AS avg_mastery_pct,

    COUNT(*) FILTER (WHERE due_date <= CURRENT_DATE)   AS due_today,
    SUM(total_reviews)                                 AS lifetime_reviews
FROM knowledge_items
WHERE user_id = $1;
```

### 1.2 PKCE OAuth2 with Local Callback Server (for OpenAI/Codex side)

**Recommended library stack:**
- `authlib>=1.3.0` — handles PKCE automatically; supports both `requests` and `httpx`
- `requests-oauthlib` — lighter alternative using `oauthlib` primitives
- Standard library `http.server`, `threading`, `webbrowser` — for the local callback server

**Complete implementation pattern:**

```python
import base64
import hashlib
import json
import secrets
import socket
import threading
import webbrowser
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import parse_qs, urlparse

import httpx

# ── Step 1: PKCE pair generation ──────────────────────────────────────────────

def generate_pkce_pair() -> tuple[str, str]:
    """Returns (code_verifier, code_challenge) using S256 method."""
    # RFC 7636: verifier must be 43–128 chars of [A-Za-z0-9\-._~]
    code_verifier = (
        base64.urlsafe_b64encode(secrets.token_bytes(64))
        .rstrip(b"=")
        .decode("ascii")
    )
    code_challenge = (
        base64.urlsafe_b64encode(
            hashlib.sha256(code_verifier.encode("ascii")).digest()
        )
        .rstrip(b"=")
        .decode("ascii")
    )
    return code_verifier, code_challenge

# ── Step 2: Local callback server ─────────────────────────────────────────────

def find_free_port() -> int:
    """Bind to port 0 to let the OS assign a free ephemeral port."""
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        return s.getsockname()[1]

class _CallbackHandler(BaseHTTPRequestHandler):
    """Captures ?code=... and ?state=... from the OAuth redirect."""
    result: dict | None = None

    def do_GET(self):
        parsed = urlparse(self.path)
        params = parse_qs(parsed.query)
        _CallbackHandler.result = {
            "code": params.get("code", [None])[0],
            "state": params.get("state", [None])[0],
            "error": params.get("error", [None])[0],
        }
        self.send_response(200)
        self.send_header("Content-Type", "text/html")
        self.end_headers()
        self.wfile.write(
            b"<h2>Authorization complete. You may close this tab.</h2>"
        )

    def log_message(self, format, *args):  # silence access logs
        pass

def _run_callback_server(server: HTTPServer):
    server.handle_request()  # handle exactly ONE request then exit
    server.server_close()

def pkce_login(
    client_id: str,
    authorization_endpoint: str,
    token_endpoint: str,
    scopes: list[str],
) -> dict:
    """
    Full PKCE authorization code flow using a local callback server.
    Returns the token response dict (access_token, refresh_token, expires_in, …).
    """
    port = find_free_port()
    redirect_uri = f"http://127.0.0.1:{port}/auth/callback"

    code_verifier, code_challenge = generate_pkce_pair()
    state = secrets.token_urlsafe(16)

    # Build the authorization URL manually (no external dependency needed)
    params = {
        "response_type": "code",
        "client_id": client_id,
        "redirect_uri": redirect_uri,
        "scope": " ".join(scopes),
        "state": state,
        "code_challenge": code_challenge,
        "code_challenge_method": "S256",
    }
    query = "&".join(f"{k}={v}" for k, v in params.items())
    auth_url = f"{authorization_endpoint}?{query}"

    # Start the one-shot local server before opening the browser
    server = HTTPServer(("127.0.0.1", port), _CallbackHandler)
    server_thread = threading.Thread(target=_run_callback_server, args=(server,), daemon=True)
    server_thread.start()

    print(f"Opening browser for authorization...")
    webbrowser.open(auth_url)
    server_thread.join(timeout=120)  # wait up to 2 minutes

    result = _CallbackHandler.result
    if not result or result.get("error"):
        raise RuntimeError(f"OAuth error: {result}")
    if result["state"] != state:
        raise RuntimeError("State mismatch — possible CSRF attack")

    # Exchange authorization code for tokens
    response = httpx.post(
        token_endpoint,
        data={
            "grant_type": "authorization_code",
            "code": result["code"],
            "redirect_uri": redirect_uri,
            "client_id": client_id,
            "code_verifier": code_verifier,  # PKCE: verifier sent here
        },
        headers={"Content-Type": "application/x-www-form-urlencoded"},
    )
    response.raise_for_status()
    return response.json()
```

### 1.3 Encrypted Local Credential Storage

**Recommended approach: `cryptography` Fernet + machine-derived key + `portalocker`**

```python
import base64
import json
import os
from pathlib import Path

from cryptography.fernet import Fernet
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

CREDENTIALS_DIR = Path.home() / ".config" / "study-kit"
CREDENTIALS_FILE = CREDENTIALS_DIR / "credentials.json.enc"
SALT_FILE = CREDENTIALS_DIR / ".salt"

def _get_or_create_salt() -> bytes:
    CREDENTIALS_DIR.mkdir(parents=True, exist_ok=True)
    if SALT_FILE.exists():
        return SALT_FILE.read_bytes()
    salt = os.urandom(16)
    SALT_FILE.write_bytes(salt)
    SALT_FILE.chmod(0o600)
    return salt

def _derive_key(password: bytes) -> bytes:
    """Derive a Fernet key from a password + stored salt via PBKDF2."""
    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=_get_or_create_salt(),
        iterations=1_200_000,  # OWASP 2025 minimum
    )
    return base64.urlsafe_b64encode(kdf.derive(password))

def _get_fernet(password: str) -> Fernet:
    return Fernet(_derive_key(password.encode()))

# Credential store: keyed by agentId
def save_credentials(agent_id: str, token_data: dict, password: str) -> None:
    """Encrypt and persist tokens for a given agentId."""
    f = _get_fernet(password)
    existing = _load_all_credentials_raw(f)
    existing[agent_id] = token_data
    encrypted = f.encrypt(json.dumps(existing).encode())
    CREDENTIALS_FILE.write_bytes(encrypted)
    CREDENTIALS_FILE.chmod(0o600)

def load_credentials(agent_id: str, password: str) -> dict | None:
    f = _get_fernet(password)
    all_creds = _load_all_credentials_raw(f)
    return all_creds.get(agent_id)

def _load_all_credentials_raw(f: Fernet) -> dict:
    if not CREDENTIALS_FILE.exists():
        return {}
    return json.loads(f.decrypt(CREDENTIALS_FILE.read_bytes()).decode())
```

**Alternative: `keyring` library** — uses the OS keychain (macOS Keychain, Windows Credential Manager, libsecret on Linux). Simpler but no agentId-organized JSON structure:

### 1.4 Token Refresh with File Locking

**Library: `portalocker>=2.8.2`** — cross-platform (macOS/Linux/Windows), context manager API, timeout support.

```python
import time
import portalocker

LOCK_FILE = CREDENTIALS_DIR / "credentials.lock"
TOKEN_EXPIRY_BUFFER = 300  # refresh 5 minutes before expiry

def is_token_expired(token_data: dict) -> bool:
    expires_at = token_data.get("expires_at", 0)
    return time.time() >= (expires_at - TOKEN_EXPIRY_BUFFER)

def refresh_token(
    agent_id: str,
    token_endpoint: str,
    client_id: str,
    password: str,
) -> dict:
    """
    Refresh the access token using file locking to prevent concurrent refreshes
    across multiple processes (e.g., parallel CLI invocations).
    """
    LOCK_FILE.parent.mkdir(parents=True, exist_ok=True)

    with portalocker.Lock(str(LOCK_FILE), mode="a", timeout=30) as _lock:
        # Re-read inside the lock; another process may have refreshed already
        token_data = load_credentials(agent_id, password)
        if token_data is None:
            raise RuntimeError(f"No credentials for agent {agent_id}")

        if not is_token_expired(token_data):
            return token_data  # someone else already refreshed it

        response = httpx.post(
            token_endpoint,
            data={
                "grant_type": "refresh_token",
                "refresh_token": token_data["refresh_token"],
                "client_id": client_id,
            },
            headers={"Content-Type": "application/x-www-form-urlencoded"},
        )
        response.raise_for_status()
        new_token = response.json()
        new_token["expires_at"] = time.time() + new_token.get("expires_in", 3600)

        save_credentials(agent_id, new_token, password)
        return new_token
```

**Key design**: always re-read from disk after acquiring the lock ("check-then-act" inside the lock). This prevents the thundering herd problem where all processes attempt a refresh simultaneously.

### 2.2 PPTX Extraction

```python
# pip install python-pptx>=1.0.0
from pptx import Presentation

def extract_text_pptx(pptx_path: str) -> str:
    prs = Presentation(pptx_path)
    slides_text = []
    for i, slide in enumerate(prs.slides, 1):
        slide_text = f"--- Slide {i} ---\n"
        for shape in slide.shapes:
            if shape.has_text_frame:
                slide_text += shape.text_frame.text + "\n"
            if shape.has_table:
                for row in shape.table.rows:
                    slide_text += "\t".join(
                        cell.text for cell in row.cells
                    ) + "\n"
        slides_text.append(slide_text)
    return "\n".join(slides_text)
```

### 2.6 Text Chunking for AI

**Decision: Recursive character splitting with 512-token chunks, 10-15% overlap**

Research from multiple 2025 RAG benchmarks shows:

| Strategy | Accuracy | Complexity | Best For |
|---|---|---|---|
| Fixed-size | Baseline | Low | Simple uniform text |
| **Recursive** | Good | Low-Medium | **General documents (recommended default)** |
| Semantic | Best (+70% vs fixed) | High | Technical/academic papers |
| Hierarchical | Best for long docs | Medium | Manuals, reports |

**Recommended defaults: 512 tokens, 50-75 token overlap (10-15%)**

```python
# pip install langchain-text-splitters>=0.3.0 tiktoken>=0.7.0
from langchain_text_splitters import RecursiveCharacterTextSplitter
import tiktoken

def chunk_text(
    text: str,
    chunk_size: int = 512,    # tokens
    chunk_overlap: int = 64,  # ~12.5% overlap
    model: str = "gpt-4",
) -> list[str]:
    """
    Chunk extracted text for AI ingestion.
    Uses tiktoken for accurate token counting.
    """
    enc = tiktoken.encoding_for_model(model)

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size,
        chunk_overlap=chunk_overlap,
        length_function=lambda t: len(enc.encode(t)),
        separators=["\n\n", "\n", ". ", "! ", "? ", " ", ""],
    )
    return splitter.split_text(text)


# Document-type-aware chunking
def chunk_document(text: str, doc_type: str) -> list[str]:
    if doc_type == "slide":  # PPTX — already chunked by slide separator
        return [s.strip() for s in text.split("--- Slide") if s.strip()]
    elif doc_type == "markdown":  # DOCX converted via mammoth
        splitter = RecursiveCharacterTextSplitter(
            chunk_size=512,
            chunk_overlap=64,
            separators=["## ", "# ", "\n\n", "\n", ". "],
        )
        return splitter.split_text(text)
    else:  # PDF, audio transcript
        return chunk_text(text)
```

**Guidance by format:**
- **PDF**: 512 tokens, 64 overlap, recursive splitting
- **PPTX**: Split naturally on slide boundaries; each slide = one chunk if under 512 tokens
- **DOCX**: Split on heading boundaries first (mammoth Markdown output), then recursive within sections
- **Audio transcript**: 512 tokens with larger overlap (128 tokens) — speech lacks hard sentence structure
- **Images (OCR output)**: Same as PDF plain text

## Task Generation Rules

**CRITICAL**: Tasks MUST be organized by user story to enable independent implementation and testing.

**Tests are OPTIONAL**: Only generate test tasks if explicitly requested in the feature specification or if user requests TDD approach.

### Checklist Format (REQUIRED)

Every task MUST strictly follow this format:

```text
- [ ] [TaskID] [P?] [Story?] Description with file path
```

**Format Components**:

1. **Checkbox**: ALWAYS start with `- [ ]` (markdown checkbox)
2. **Task ID**: Sequential number (T001, T002, T003...) in execution order
3. **[P] marker**: Include ONLY if task is parallelizable (different files, no dependencies on incomplete tasks)
4. **[Story] label**: REQUIRED for user story phase tasks only
   - Format: [US1], [US2], [US3], etc. (maps to user stories from spec.md)
   - Setup phase: NO story label
   - Foundational phase: NO story label  
   - User Story phases: MUST have story label
   - Polish phase: NO story label
5. **Description**: Clear action with exact file path

**Examples**:

- ✅ CORRECT: `- [ ] T001 Create project structure per implementation plan`
- ✅ CORRECT: `- [ ] T005 [P] Implement authentication middleware in src/middleware/auth.py`
- ✅ CORRECT: `- [ ] T012 [P] [US1] Create User model in src/models/user.py`
- ✅ CORRECT: `- [ ] T014 [US1] Implement UserService in src/services/user_service.py`
- ❌ WRONG: `- [ ] Create User model` (missing ID and Story label)
- ❌ WRONG: `T001 [US1] Create model` (missing checkbox)
- ❌ WRONG: `- [ ] [US1] Create User model` (missing Task ID)
- ❌ WRONG: `- [ ] T001 [US1] Create model` (missing file path)
